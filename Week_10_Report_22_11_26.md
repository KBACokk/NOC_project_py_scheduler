## 1. Исходный контекст и задачи недели

На 9-й неделе было подтверждено ключевое функциональное требование: выделение `StatsManager` в отдельный модуль сохранило численную инвариантность результатов симуляции (подтверждено пошаговым совпадением на прогонах в 5000 TTI).

Однако архитектурно система всё ещё находилась на этапе механического разделения (**Этап E0: Extraction**):
* `StatsManager` напрямую опрашивал жестко закодированные структуры планировщика, AMC, PDCCH и менеджера очередей.
* Для сбора телеметрии из других доменных модулей (`CHANNEL_MODEL`, `MOBILITY_MODEL`, `TRAFFIC_MODEL`, `HARQ`) потребовалось бы продолжать модифицировать ядро `SIMULATION_MANAGER.py` или `STATS_MANAGER.py`, что нарушало принцип открытости/закрытости (**Open-Closed Principle, OCP**) и создавало постоянные конфликты слияния в Git при параллельной работе команды.
* В сценариях запуска выявились скрытые регрессионные дефекты конфигурации (отсутствие сеттеров интервалов обновления канала/мобильности и некорректный сброс флага устаревшего трафика при работе с многоуровневыми буферами QoS).

**Основные задачи 10-й недели:**
1. **Спроектировать и реализовать контракт коллектора статистики (`IStatsCollector` / `BaseStatsCollector`)** и реестр коллекторов внутри `StatsManager`.
2. **Обеспечить обратную совместимость (Legacy Fallbacks):** гарантировать непрерывную работу симулятора со старыми модулями планировщика и очередей до их перевода на целевые контракты.
3. **Устранить регрессионные ошибки в `SimulationManager`:** восстановить методы управления интервалами и обеспечить корректную инициализацию стеков RLC/PDCP в режиме `LayeredBufferManager`.
4. **Разработать архитектурный регламент для команды (`COLLECTOR_CONTRACT_GUIDE.md`):** зафиксировать дорожную карту E0 vs E1, правила именования метрик, уровни детализации `MetricLevel` и шаблоны модульного тестирования.
5. **Синхронизировать кодовую базу с актуальной веткой `dev`:** устранить ложные диффы в чужих компонентах (`SCHEDULER.py`), очистить репозиторий от локальных артефактов прогонов и подготовить чистый Pull Request.

## 2. Выполненные работы

### 2.1. Универсальный контракт коллектора (`IStatsCollector` и `BaseStatsCollector`)

В модуль `PyScheduler/STATS_MANAGER.py` заложена архитектурная основа целевого этапа **E1**:
* **Протокол `IStatsCollector` (`@runtime_checkable Protocol`):**
  * `get_collector_name() -> str` — уникальный строковый идентификатор подсистемы в нижнем регистре;
  * `collect_aggregated(tti, level) -> Dict[str, Any]` — сбор скалярных системных показателей текущего такта;
  * `collect_detailed(tti, level) -> Optional[Dict[Any, Dict[str, Any]]]` — сбор поабонентных (per-UE) метрик;
  * `collect_custom_records(tti, level) -> Optional[Any]` — сбор специфичных многомерных матриц (QoS, per-QCI).
* **Базовый класс `BaseStatsCollector`:** предоставляет реализации по умолчанию для опциональных методов, снижая порог входа для разработчиков модулей.
* **Соглашение об именовании метрик:** введён обязательный префикс для ключей каждого модуля (`ch_`, `mob_`, `traf_`, `buf_`, `harq_`, `sch_`, `amc_`, `pdcch_`), исключающий коллизии имен при формировании плоского системного отчёта.
* **Градация детализации `MetricLevel`:**
  * `NONE` — полное отключение сбора модуля (0% накладных расходов CPU);
  * `BASIC` — ключевые скаляры (среднее, сумма, счётчики) для длительных прогонов (50 000+ TTI, <1% CPU);
  * `ADVANCED` — расширенная статистика (min, max, std, квантили, эффективность);
  * `FULL` — включение детальной поабонентной телеметрии `collect_detailed()`.

### 2.2. Реестр коллекторов и динамический экспорт

В класс `StatsManager` внедрён механизм реестра:
* Методы `register_collector(collector, level)` и `has_collector(name)`.
* В методе `collect(tti)` менеджер обходит зарегистрированные коллекторы, запрашивает данные в соответствии с сконфигурированным уровнем и сохраняет их в снимок такта.
* **Динамическое формирование колонок:** заголовки системного CSV-файла строятся адаптивно по ключам, возвращенным коллекторами. Подключение нового модуля больше не требует изменения логики экспорта в `StatsManager`.
* **Изоляция данных:** снимки `history`, `detailed_history` и `qos_history` сохраняются через `deepcopy`, что гарантирует иммутабельность исторических данных при мутации структур планировщика на последующих TTI.

### 2.3. Сохранение обратной совместимости (Legacy Fallbacks)

Чтобы переход на новую систему сбора телеметрии не ломал существующий пайплайн симуляции:
* Сохранены встроенные провайдеры-адаптеры (`ISchedulerStatsProvider`, `IAmcStatsProvider`, `IPdcchStatsProvider`, опрос буферов).
* Если для домена не зарегистрирован внешний `IStatsCollector`, `StatsManager` обращается к переданным объектам планировщика и буферов через legacy-каналы (`_collect_scheduler()`, `_collect_amc()`, `_collect_pdcch()`, `_collect_qos()`).
* Таким образом, ядро симулятора готово к поэтапному подключению независимых коллекторов от команд без остановки текущих исследований.
