# План развития модуля Simulation Manager и Тестовый комплекс

## 1. Предложения для своего модуля

### Ticket - 01  - Исправление дефекта запуска и переход на структурированное логирование

- **Проблема сейчас:** Тело метода `start_simulation()` физически обернуто в блок `if self._to_file:`. Запуск моделирования без сохранения в файл `output.txt` невозможен (симуляция завершается мгновенно, не выполняя ни одного TTI, см. `audit.md::AUD-001`). Прямая подмена `sys.stdout` и `sys.stderr` ломает окружение в интерактивных средах и блокирует создание чистого CLI (см. `audit.md::AUD-004`). Внешнее условие `update_interval` маскирует частоту обновления радиоканала (см. `audit.md::AUD-007`).
- **Цель:** Обеспечить штатный запуск симуляции при любых флагах логирования; заменить глобальный редирект системных потоков на стандартный `logging.Logger`.
- **Предлагаемое изменение:**
  1. Вынести блок валидации, создания ресурсной сетки, планировщика и цикл `for tti in range(...)` из-под условия `if self._to_file:`.
  2. Использовать `logger = logging.getLogger("PyScheduler.SimManager")`. При флаге `to_file=True` добавлять `FileHandler("output.txt")`, не трогая системные `sys.stdout` и `sys.stderr`.
  3. В `run_tti` вызывать `UPDATE_ALL_USERS` на каждом TTI, предоставив проверку индивидуальных периодов `mob_interval` и `ch_interval` самому методу `UPDATE_ALL_USERS`.
- **Задача:** Исправление отступов, настройка логгера и фикс таймингов вызова.
- **Входы и выходы:** Сигнатура `start_simulation()` сохраняется. Возвращает управление вызывающему коду при любом значении `_to_file`.
- **Зависимости:** Фронтенд (CLI) получает предсказуемый вывод в консоль.
- **Шаги:**
  1. Устранить ошибку индентации в `PyScheduler/SIMULATION_MANAGER.py::SimulationManager.start_simulation`.
  2. Заменить переопределение `sys.stdout` на `FileHandler` логгера.
  3. Проверить корректность вызовов `UPDATE_ALL_USERS` при раздельных интервалах.

### Ticket - 02 - Устранение задвоения телеметрии в `StatsManager`

- **Проблема сейчас:** В главном цикле `start_simulation()` вызов `self.stats_manager.collect(tti)` выполняется дважды за один TTI (на строках 1293 и 1324), из-за чего в историю и результирующий CSV-файл записываются дубликаты строк (см. `audit.md::AUD-002`).
- **Цель:** Гарантировать запись ровно одного снапшота метрик на каждый интервал `collect_interval`.
- **Предлагаемое изменение:** Удалить дублирующий вызов `self.stats_manager.collect(tti)` на строке 1324 `SIMULATION_MANAGER.py`.
- **Задача:** Точечная правка строки вызова и добавление регрессионного теста.
- **Входы и выходы:** Контракты файлов `manager_stats.csv` и `manager_stats_detailed.csv` сохраняются без изменений формата, но строки TTI становятся уникальными.
- **Зависимости:** `PLOT_METRICS.py` и аналитические скрипты получают корректные временные ряды без ложных повторов.
- **Шаги:**
  1. Удалить строку 1324 в `SIMULATION_MANAGER.py`.
  2. Добавить проверку длины истории в юнит-тесты.

### Ticket - 03- Проектирование публичного API и сценариев для CLI 

- **Проблема сейчас:** Запуск симуляции возможен только путем ручной правки кода в `TEST_MODULES.py`. Отсутствует декларативный интерфейс конфигурации сценария для передачи параметров через командную строку (`--duration`, `--algo`, `--num-ue`, `--bandwidth`, `--seed`).
- **Цель:** Предоставить Фронтенду программный фасад `SimulationFacade` и датакласс сценария `SimulationScenario` для бесшовной интеграции с CLI.
- **Задача:**  Программный фасад, сборка сценария и датаклассы. Парсинг CLI аргументов (`argparse`/`click`)
- **Входы и выходы:**
  - Вход: объект `SimulationScenario` или словарь аргументов CLI.
  - Выход: объект `SimulationResult` со ссылками на сгенерированные файлы и ключевые KPI.
- **Шаги:**
  1. Согласовать имена параметров CLI и структуру `SimulationScenario` с Никой.
  2. Реализовать `SimulationFacade.run_scenario` в `SIMULATION_MANAGER.py`.
  3. Провести сквозное тестирование вызова из тестового CLI скрипта.
