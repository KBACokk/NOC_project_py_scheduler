# План развития модуля Simulation Manager и Тестовый комплекс

### FEAT-001 — Исправление дефекта запуска и переход на структурированное логирование

- **Проблема сейчас:** Тело метода `start_simulation()` физически обернуто в блок `if self._to_file:`. Запуск моделирования без сохранения в файл `output.txt` невозможен (симуляция завершается мгновенно, не выполняя ни одного TTI, см. `audit.md::AUD-001`). Прямая подмена `sys.stdout` и `sys.stderr` ломает окружение в интерактивных средах и блокирует создание чистого CLI (см. `audit.md::AUD-004`). Внешнее условие `update_interval` маскирует частоту обновления радиоканала (см. `audit.md::AUD-007`).
- **Цель:** Обеспечить штатный запуск симуляции при любых флагах логирования; заменить глобальный редирект системных потоков на стандартный `logging.Logger`.
- **Предлагаемое изменение:**
  1. Вынести блок валидации, создания ресурсной сетки, планировщика и цикл `for tti in range(...)` из-под условия `if self._to_file:`.
  2. Использовать `logger = logging.getLogger("PyScheduler.SimManager")`. При флаге `to_file=True` добавлять `FileHandler("output.txt")`, не трогая системные `sys.stdout` и `sys.stderr`.
  3. В `run_tti` вызывать `UPDATE_ALL_USERS` на каждом TTI, предоставив проверку индивидуальных периодов `mob_interval` и `ch_interval` самому методу `UPDATE_ALL_USERS`.
- **Входы и выходы:** Сигнатура `start_simulation()` сохраняется. Возвращает управление вызывающему коду при любом значении `_to_file`.
- **Шаги:**
  1. Устранить ошибку индентации в `PyScheduler/SIMULATION_MANAGER.py::SimulationManager.start_simulation`.
  2. Заменить переопределение `sys.stdout` на `FileHandler` логгера.
  3. Проверить корректность вызовов `UPDATE_ALL_USERS` при раздельных интервалах.

### FEAT-002 — Устранение задвоения телеметрии в `StatsManager`

- **Проблема сейчас:** В главном цикле `start_simulation()` вызов `self.stats_manager.collect(tti)` выполняется дважды за один TTI (на строках 1293 и 1324), из-за чего в историю и результирующий CSV-файл записываются дубликаты строк (см. `audit.md::AUD-002`).
- **Цель:** Гарантировать запись ровно одного снапшота метрик на каждый интервал `collect_interval`.
- **Предлагаемое изменение:** Удалить дублирующий вызов `self.stats_manager.collect(tti)` на строке 1324 `SIMULATION_MANAGER.py`.
- **Входы и выходы:** Контракты файлов `manager_stats.csv` и `manager_stats_detailed.csv` сохраняются без изменений формата, но строки TTI становятся уникальными.
- **Зависимости:** `PLOT_METRICS.py` и аналитические скрипты получают корректные временные ряды без ложных повторов.
- **Шаги:**
  1. Удалить строку 1324 в `SIMULATION_MANAGER.py`.
  2. Добавить проверку длины истории в юнит-тесты.

### FEAT-003 — Создание автоматизированного тестового набора ядра оркестратора (`tests/simulation_manager_tests`)
- **Статус:** обсуждается
- **Проблема сейчас:** В каталоге `tests/` полностью отсутствуют автотесты на `SimulationManager`, `StatsManager` и метод `run_tti` (см. `audit.md::AUD-005`). Падения выявляются только вручную.
- **Цель:** Обеспечить 100% стабильность жизненного цикла симулятора в continuous integration.
- **Предлагаемое изменение:** Создать каталог `PyScheduler/tests/simulation_manager_tests/` со следующими тест-сьютами:
  - `test_manager_config.py` — проверка валидации обязательных параметров (`_check_required_parameters`), реакция на отрицательные и некорректные типы таймингов.
  - `test_manager_lifecycle.py` — проверка пошагового выполнения `run_tti`, синхронизации `GLOBALS.CURRENT_TIME`, обновления буферов и списания данных.
  - `test_stats_manager.py` — проверка сбора телеметрии без задвоений.
- **Входы и выходы:** Тестовые функции `test_*()` под управлением `pytest`.
- **Зависимости:** `pytest`, тестовые фикстуры с mock-объектами БС и UE.
- **Шаги:**
  1. Разработать легковесные фикстуры в `conftest.py` (минимальная БС и 2 UE).
  2. Написать юнит-тесты валидации и жизненного цикла.
  3. Добавить регрессионный тест на проверку отсутствия дублей в `StatsManager`.

### FEAT-004 — Архитектурная изоляция контекста симулятора для параллельных вычислений
- **Проблема сейчас:** Симулятор использует разделяемое глобальное состояние (`GLOBALS.CURRENT_TIME`, синглтон `MapBorders._instance`). Это исключает параллельный запуск нескольких симуляций в одном адресном пространстве (например, для серии экспериментов Монте-Карло или многократного прогона с разными seed).
- **Цель:** Изолировать состояние каждого запуска внутри объекта контекста `SimulationContext`, подготовив ядро к масштабированию на параллельные процессы (`concurrent.futures.ProcessPoolExecutor`).
- **Предлагаемое изменение:**
  1. Передать `current_time` явно через контекст исполнения, устранив зависимость от глобальной мутации `GLOBALS.CURRENT_TIME`.
  2. Перевести `MapBorders` из глобального синглтона в объект сотовой топологии, хранящийся внутри экземпляра `SimulationManager` или передаваемый в `BaseStation`.
  3. Реализовать параллельный батч-раннер `BatchSimulationRunner` для одновременного выполнения N независимых прогонов на разных ядрах CPU.
- **Входы и выходы:** Список конфигураций сценариев `List[SimulationScenario]` -> список результатов `List[SimulationResult]`.
- **Зависимости:** Согласование со всеми разработчиками модулей (отказ от глобального `GLOBALS.CURRENT_TIME`).
- **Шаги:**
  1. Провести аудит использования `GLOBALS` во всех модулях (в первую очередь с Кириллом Б.)
  2. Реализовать параллельный раннер для пакетных экспериментов.
