Этап 0
CQI Refresh & Синхронизация радиокарты соты
_refresh_cqi(tti, users) O(N_UE) Период: wb_cqi_upd_interval TTI

Подготовительный этап перед запуском цикла планирования. Синхронизирует карту качества радиоканала CQIMap для всех подключенных к соте терминалов. Обновляет широкополосный wb_cqi (1–15) и вектор субдиапазонных sb_cqi[] для каждого RBG сетки частот. Устраняет тяжелые повторные обращения к моделям замирания радиоканала в цикле распределения.

⚙️ Пошаговый алгоритм выполнения
  1. Проверка тайминга обновления: Проверяется условие tti % self.wb_cqi_upd_interval == 0. Если интервал не наступил, этап пропускается без накладных расходов.
  2. Итерация по базе соты: Для каждого зарегистрированного терминала user извлекается его идентификатор UE_ID.
  3. Считывание CQI: Извлекаются мгновенные значения широкополосного CQI (wideband) и субдиапазонных CQI per RBG из радиомодели CHANNEL_MODEL.
  4. Кэширование в CQIMap: Создается или обновляется экземпляр CQIMap(wb_cqi, sb_cqi_list, last_update_tti) в словаре self.cqi_map[ue_id].
Математическая модель:
SINR на RBG k: γi,k = (Ptx · |hi,k|2) / (Ii,k + σ2)
CQI Mapping: CQIi,k = argmaxc ∈ {1..15} { BLER(c, γi,k) ≤ 0.10 }
📋 Контракт данных и параметры
Входные данныеtti: int, users: List[Dict] (поля UE_ID, cqi, sbb_cqi)
Выходные данныеСловарь self.cqi_map: Dict[int, CQIMap]
Поле CQIMapwb_cqi: int, sb_cqi: List[int], tti: int
💡 Числовой пример из симуляции
Терминал UE #04 имеет средний SINR = +14.2 дБ. Модель радиоканала сопоставляет ему Wideband CQI = 11 (64-QAM, кодовая скорость 0.754). Субдиапазоны RBG 0–3 имеют CQI = 12, а RBG 4–7 — CQI = 10. Все значения записываются в self.cqi_map[4] за один проход.
⚠️ Инженерный нюанс реализации
Если бы планировщик опрашивал модель замираний Рэлея напрямую в момент распределения каждого RBG, сложность алгоритма возросла бы в 17 раз (по числу RBG). Кэширование радиокарты в начале TTI экономит до 60% времени CPU симулятора.
# PyScheduler/SCHEDULER.py: Синхронизация карты качества радиоканала def _refresh_cqi(self, tti: int, users: List[Dict]) -> None: for user in users: ue_id = user['UE_ID'] wb_cqi = user.get('cqi', 1) sb_cqi = user.get('sbb_cqi', [wb_cqi] * self.lte_grid.rbg_count) self.cqi_map[ue_id] = CQIMap(wb_cqi=wb_cqi, sb_cqi=sb_cqi, updated_tti=tti)
Этап 1
Eligibility Filter & Первичная отбраковка кандидатов
_filter_eligible_ues(tti, users) O(N_UE) Выход: eligible_ues

Первичная отсекающая фильтрация пула соты. Исключает терминалы, которые не могут или не требуют передачи в текущем субкадре: терминалы с пустыми буферами передачи (нет данных) и терминалы вне зоны устойчивой радиосвязи (CQI = 0). Также производит обязательный сброс мгновенной скорости current_dl_throughput для корректной телеметрии.

⚙️ Пошаговый алгоритм выполнения
  1. Сброс телеметрии скорости: Для всех терминалов в соте вызывается user['ue'].current_dl_throughput = 0. Это гарантирует, что неотсортированные абоненты покажут нулевую мгновенную скорость.
  2. Проверка наличия буфера BS: Вызов buffer_manager.ue_has_buffer(ue_id). Если буфер очереди не зарегистрирован в BaseStation, UE отбрасывается.
  3. Проверка объема данных: Проверка user['bs_buffer_size'] > 0. Абоненты, завершившие прием трафика, отсекаются.
  4. Проверка валидности радиоканала: Проверка 1 ≤ CQI ≤ 15. Значение CQI = 0 означает потерю синхронизации (Out of Coverage, SINR < -6 дБ).
  5. Формирование допуска: Успешно прошедшие терминалы добавляются в результирующий список eligible_ues.
Математическое условие допуска (Eligibility Indicator):
Ei = 𝕀(HasBufferi) · 𝕀(Bi > 0) · 𝕀(1 ≤ CQIi ≤ 15) ∈ {0, 1}
📋 Контракт данных и параметры
Входные данныеusers: List[Dict] (100 зарегистрированных терминалов)
Выходные данныеeligible_ues: List[Dict] (отфильтрованные кандидаты)
Критерий выходаЕсли eligible_ues == [] → возврат _empty_result()
💡 Числовой пример из симуляции
В соте 100 UE. У 35 терминалов буфер базовой станции пуст (пакеты не поступали от TRAFFIC_MODEL). У 20 терминалов CQI = 0 (находятся за границей соты на расстоянии > 1200 м). В результате 55 терминалов мгновенно отсеиваются, а в eligible_ues переходят 45 кандидатов.
⚠️ Инженерный нюанс реализации
Сброс current_dl_throughput = 0 строго необходим именно здесь. Если этого не сделать, терминал, получивший пакет в прошлом такте, сохранит старое ненулевое значение в графиках PLOT_METRICS, что приведет к ложным всплескам пропускной способности.
# PyScheduler/SCHEDULER.py: Фильтрация допущенных к планированию UE def _filter_eligible_ues(self, tti: int, users: List[Dict]) -> List[Dict]: for user in users: user['ue'].current_dl_throughput = 0 eligible = [] buf_mgr = self.lte_grid.bs.buffer_manager for user in users: ue_id = user['UE_ID'] cqi = self._get_wb_cqi(ue_id) if buf_mgr.ue_has_buffer(ue_id) and user['bs_buffer_size'] > 0 and 1 <= cqi <= 15: eligible.append(user) return eligible
Этап 2
Active Window & Скользящее окно обслуживания FIFO
_update_active_window() / filter_by_window() O(window_size) Ротация: FIFO Tail

Механизм регулирования вычислительной нагрузки процессора базовой станции (CPU/DSP) и предотвращения голодания очередей (anti-starvation). Ограничивает число одновременно рассматриваемых кандидатов размером скользящего окна window_size (обычно 10–20 UE), организуя циклическую ротацию абонентов.

⚙️ Пошаговый алгоритм выполнения
  1. Синхронизация FIFO-очереди: Новые абоненты из eligible_ues, которых еще нет в очереди active_ue_queue, добавляются в ее конец.
  2. Удаление неактивных: Абоненты, чей буфер опустел или потерял CQI, исключаются из отслеживания.
  3. Срез текущего окна: Функция filter_by_window() отбирает первые window_size абонентов из очереди: windowed_ues = active_ue_queue[:window_size].
  4. Циклическая ротация: Абоненты, обслуженные в текущем субкадре, перемещаются в хвост FIFO-очереди, уступая место в окне кандидатам следующего TTI.
Ограничение мощности множества кандидатов:
|Windowed_UEs(t)| = min( |Eligible_UEs(t)|, window_size ) ≤ 20
Позиция в очереди: Posi(t+1) = (Posi(t) - window_size) mod |Active_Queue|
📋 Контракт данных и параметры
Входные данныеeligible_ues: List[Dict] (45 кандидатов)
Выходные данныеwindowed_ues: List[Dict] (максимум window_size элементов)
Параметр размераself.window_size: int (по умолчанию 20)
💡 Числовой пример из симуляции
Из 45 допущенных абонентов первые 20 попадают в windowed_ues для немедленного расчета приоритетов в текущем такте TTI #14. Оставшиеся 25 абонентов остаются в начале очереди и гарантированно получат первоочередной допуск в окне такта TTI #15.
⚠️ Инженерный нюанс реализации
Без скользящего окна сортировка 500+ абонентов по алгоритму Proportional Fair и последующий перебор частотных RBG приводили бы к экспоненциальному росту времени расчетов. Окно FIFO гарантирует фиксированное время отклика ≤ 1 мс, что критично для жесткого реального времени MAC.
# PyScheduler/SCHEDULER.py: Обновление и срез скользящего окна def filter_by_window(self, eligible_ues: List[Dict]) -> List[Dict]: if not self.active_ue_queue: return eligible_ues[:self.window_size] allowed_ids = {u['UE_ID'] for u in eligible_ues} windowed = [u for u in self.active_ue_queue if u['UE_ID'] in allowed_ids] return windowed[:self.window_size]
Этап 3
Priority Calculation & Математическое ядро алгоритмов
_calculate_priorities(windowed_ues, tti) TD: O(W) | FD: O(W × N_RBG) Метрика: priority_calc_time_us

Алгоритмическое сердце планировщика ресурсов. На этом этапе вычисляется метрика приоритета для каждого кандидата из окна обслуживания. В зависимости от выбранного алгоритма (Round Robin, Best CQI, Proportional Fair или их частотно-селективных FD-аналогов) вычисляется скалярный приоритет или матрица субдиапазонных метрик размерностью [N_UE × N_RBG].

⚙️ Пошаговый алгоритм выполнения
  1. Старт профилировщика: Фиксируется начальное время через t_priority_start = time.perf_counter().
  2. Расчет мгновенной скорости Ri(t): Через модуль AMC (Adaptive Modulation and Coding) оценивается потенциальное число бит/РБ в зависимости от CQI: bits_per_rb = amc.GET_BITS_PER_RB(cqi).
  3. Вычисление формулы политики:
    • Round Robin: Метрика базируется на порядке в очереди: Pi = queue_index.
    • Best CQI: Метрика равна wideband CQI или ожидаемой скорости: Pi = CQIi.
    • Proportional Fair: Метрика балансирует мгновенную и среднюю скорость: Pi = Ri(t) / Ti(t).
  4. Сохранение в структуре кандидата: Поле user['priority'] = round(priority_val, 4).
  5. Замер тайминга: Вычисление priority_calc_time_us для системной телеметрии.
Математические модели планирования:
• Proportional Fair (PF): Pi(t) = Ri(t) / (T̅i(t))α, где α ≥ 1
• FD Proportional Fair: Pi,k(t) = Ri,k(t) / T̅i(t) для каждого RBG k
• Best CQI: Pi(t) = argmax SINRi(t)
• Round Robin: Pi(t) = (t - last_scheduled_ttii)
📋 Контракт данных и параметры
Входные данныеwindowed_ues: List[Dict], модуль AMC, статистика скоростей
Выходные данныеСписок prioritized_ues с добавленным ключом 'priority'
Тайминг замераself.priority_calc_time_us: float (микросекунды)
💡 Числовой пример из симуляции (PF)
Терминал UE #01 имеет мгновенную скорость R1 = 3.2 Мбит/с и среднюю T̅1 = 1.12 Мбит/с → Приоритет P1 = 3.2 / 1.12 = 2.857.
Терминал UE #07 имеет R7 = 1.4 Мбит/с и среднюю T̅7 = 0.80 Мбит/с → P7 = 1.4 / 0.80 = 1.750.
Терминал UE #01 получает преимущество при отборе в PDSCH.
⚠️ Инженерный нюанс реализации
При холодном старте или долгом простое терминала его средняя скорость T̅i(t) стремится к нулю. Чтобы избежать деления на ноль, в коде используется защитная эпсилон-константа: max(ue.average_throughput, 1e-6). Это гарантирует максимальный всплеск приоритета для долго ожидавших терминалов.
# PyScheduler/SCHEDULER.py (ProportionalFairScheduler) def _calculate_priorities(self, windowed_ues: List[Dict], tti: int) -> List[Dict]: for user in windowed_ues: ue = user['ue'] cqi = self._get_wb_cqi(user['UE_ID']) achievable_rate = self.amc.GET_BITS_PER_RB(cqi) * self.lte_grid.rb_per_slot avg_throughput = max(ue.average_dl_throughput, 1.0) user['priority'] = achievable_rate / avg_throughput return windowed_ues
Этап 4
Priority List & Сортировка по убыванию приоритета
_form_priority_list(prioritized_ues, tti) O(W · log W) Лимит: max_dl_ue_tti

Ранжирование кандидатов по невозрастанию метрики приоритета с использованием стабильного гибридного алгоритма Timsort (reverse=True). Ограничение отсортированного списка системным аппаратным лимитом max_dl_ue_tti, отражающим физические возможности DSP базовой станции по мультиплексированию терминалов за 1 мс.

⚙️ Пошаговый алгоритм выполнения
  1. Фиксация тайминга сортировки: Вызов t_sort_start = time.perf_counter().
  2. Сортировка списка кандидатов: Применение встроенной функции: priority_list = sorted(prioritized_ues, key=lambda u: u.get('priority', 0), reverse=True).
  3. Аппаратный срез списка: Усечение до порога базовой станции: priority_list = priority_list[:self.max_dl_ue_tti] (обычно 8–10 UE).
  4. Расчет средней метрики кадра: Вычисление среднего приоритета отобранных кандидатов _last_avg_priority_value для мониторинга в PLOT_METRICS.
  5. Замер тайминга: Расчет priority_sort_time_us в микросекундах.
Ранжирование и усечение множества:
Psorted = (u(1), u(2), ..., u(W)), где P(u(1)) ≥ P(u(2)) ≥ ... ≥ P(u(W))
Priority_List = { u(j) ∈ Psorted | 1 ≤ j ≤ min(W, max_dl_ue_tti) }
📋 Контракт данных и параметры
Входные данныеprioritized_ues: List[Dict] (20 кандидатов из окна)
Выходные данныеpriority_list: List[Dict] (длиной ≤ max_dl_ue_tti)
Системный лимитself.max_dl_ue_tti: int (по умолчанию 10)
💡 Числовой пример из симуляции
Из 20 кандидатов окна формируется ранжированный список с приоритетами от 3.42 до 0.35. При лимите max_dl_ue_tti = 10 первые 10 кандидатов попадают в priority_list. Кандидаты с рангами 11–20 отсекаются от участия в текущем субкадре.
⚠️ Инженерный нюанс реализации
В физических базовых станциях LTE/5G процессор L1/L2 ограничен количеством одновременно формируемых транспортных блоков (TB) и размером формата DCI. Параметр max_dl_ue_tti точно эмулирует это аппаратное ограничение базовой станции.
# PyScheduler/SCHEDULER.py: Ранжирование и ограничение кандидатов def _form_priority_list(self, prioritized_ues: List[Dict], tti: int) -> List[Dict]: priority_list = sorted(prioritized_ues, key=lambda u: u.get('priority', 0), reverse=True) if self.max_dl_ue_tti is not None: priority_list = priority_list[:self.max_dl_ue_tti] return priority_list
Этап 4.5
PDSCH Estimation & Предотвращение напрасной траты CCE
_apply_pdsch_estimation(priority_list, tti) O(K) Порог: 95% от доступных PRB

Ключевая инновация планировщика v2.1.0 — эвристический механизм досрочного отсечения (Early Stopping). Оценивает совокупную потребность кандидатов в ресурсных блоках PRB по их широкополосному CQI и размеру буфера. Прекращает отбор кандидатов, как только суммарный спрос достигает 95% емкости соты. Предотвращает выделение ценных элементов PDCCH (CCE) абонентам, которым гарантированно не хватит физических PRB в эфире.

⚙️ Пошаговый алгоритм выполнения
  1. Расчет порога отсечения: Вычисляется порог pdsch_threshold = total_rb * 0.95 (например, 50 × 0.95 = 47.5 PRB для полосы 10 МГц).
  2. Итерация по приоритетному списку: Проход по кандидатам priority_list строго в порядке невозрастания приоритета.
  3. Оценка потребности в RB:
    • Определение бит на блок: bits_per_rb = amc.GET_BITS_PER_RB(cqi).
    • Расчет необходимых блоков: rb_needed = min(buffer_bits // bits_per_rb, total_rb).
  4. Проверка порога ранней остановки:
    • Первый кандидат (idx == 0) всегда принимается.
    • Если estimated_rb + rb_needed >= pdsch_threshold, добавление кандидатов прекращается!
  5. Формирование отфильтрованного списка: Возвращается priority_list_filtered, защищенный от перерасхода CCE.
Критерий досрочного прекращения (Early Stopping Rule):
E_PDSCH = ∑i=1..m min( ⌊ (Bi · 8) / BitsPerRB(CQIi) ⌋, NPRB )
Останов при условии: E_PDSCH + rb_neededm+1 ≥ 0.95 · NPRB
📋 Контракт данных и параметры
Входные данныеpriority_list: List[Dict] (10 ранжированных UE)
Выходные данныеpriority_list_filtered: List[Dict] (обычно 6–8 UE)
Порог емкостиpdsch_threshold = total_rb * 0.95 (5% резерв overhead)
💡 Числовой пример из симуляции
В соте 50 PRB. Порог 95% = 47.5 PRB. Первые 6 кандидатов суммарно запрашивают 10 + 12 + 8 + 6 + 8 + 4 = 48 PRB. Условие ≥ 47.5 сработало. Кандидаты #7, #8, #9 и #10 отсекаются здесь. Они не тратят ресурсы управляющего канала PDCCH!
⚠️ Почему это критично (Борьба с CCE Waste)
В традиционных планировщиках без Этапа 4.5 кандидатам #7–#10 выделились бы элементы CCE на этапе PDCCH. Но на этапе PDSCH свободных PRB уже не осталось бы! В результате CCE были бы сожжены впустую, лишив ресурсов восходящие каналы или ретрансляции HARQ.
# PyScheduler/SCHEDULER.py: Эвристическая оценка емкости PDSCH def _apply_pdsch_estimation(self, priority_list: List[Dict], tti: int) -> List[Dict]: total_rb = self.lte_grid.rb_per_slot estimated_rb = 0.0 selected_ues = [] pdsch_threshold = total_rb * 0.95 for idx, user in enumerate(priority_list): cqi = self._get_wb_cqi(user['UE_ID']) rb_needed = min((user['bs_buffer_size'] * 8) // self.amc.GET_BITS_PER_RB(cqi), total_rb) if idx == 0: selected_ues.append(user); estimated_rb += rb_needed; continue if estimated_rb + rb_needed >= pdsch_threshold: break selected_ues.append(user); estimated_rb += rb_needed return selected_ues
Этап 5
PDCCH Allocation & Выделение элементов канала управления CCE
_allocate_pdcch(priority_list_filtered) O(K) Счетчик блокировок: sch_pdcch_blocked_count

Выделение ресурсов физического канала управления Downlink Control Channel (PDCCH) с использованием модуля PDCCHManager. Каждый абонент должен получить управляющее сообщение DCI (Downlink Control Information) с указанием назначенных ему PRB и схемы MCS. Число выделяемых CCE определяется уровнем агрегации (Aggregation Level: 1, 2, 4 или 8) в строгой зависимости от радиоканала CQI.

⚙️ Пошаговый алгоритм выполнения
  1. Сброс пула CCE на новый TTI: Вызов pdcch_manager.reset_tti() очищает битовую карту доступных CCE.
  2. Определение Aggregation Level: Для каждого кандидата вызывается required_cce = pdcch_manager.get_aggregation_level(cqi). Чем ниже CQI, тем выше избыточность помехоустойчивого кодирования и больше требуется CCE.
  3. Попытка выделения CCE: Вызов pdcch_manager.allocate_cce(ue_id, required_cce). Менеджер выделяет непрерывный блок CCE, кратный уровню агрегации.
  4. Фиксация успеха или блокировки:
    • При успехе: user['allocated_cce'] = required_cce, кандидат переходит в ues_with_pdcch.
    • При нехватке CCE: кандидат блокируется! Счетчик sch_pdcch_blocked_count += 1.
Таблица соответствия CQI → Aggregation Level (3GPP TS 36.213):
• CQI 13..15 → AL = 1 CCE (Отличный сигнал, минимальные накладные расходы)
• CQI 10..12 → AL = 2 CCE (Хороший сигнал)
• CQI 7..9   → AL = 4 CCE (Средний сигнал)
• CQI 1..6   → AL = 8 CCE (Слабый сигнал на краю соты, максимальная защита)
📋 Контракт данных и параметры
Входные данныеpriority_list_filtered: List[Dict]
Выходные данныеues_with_pdcch: List[Dict] с полем allocated_cce
Бюджет CCE сотыОпределяется шириной полосы и PCFICH (обычно 20–28 CCE)
💡 Числовой пример из симуляции
Доступный пул = 24 CCE. Первые 6 UE с CQI ≥ 10 требуют суммарно 1+2+1+2+1+1 = 8 CCE. Кандидат #7 с CQI 8 требует 4 CCE (суммарно 12). Кандидат #8 с CQI 3 (край соты) требует 8 CCE (суммарно 20). Кандидат #9 с CQI 4 тоже требует 8 CCE, но осталось всего 4 CCE → Блокировка PDCCH! Кандидат #9 отсекается.
⚠️ Архитектурное различие планировщиков
В планировщиках BestCQI и ProportionalFair выделение PDCCH происходит до назначения частот (concurrent allocation). В RoundRobin этот метод работает как pass-through, поскольку RoundRobin выделяет PDCCH последовательно внутри шага _allocate_pdsch().
# PyScheduler/SCHEDULER.py: Выделение CCE канала управления PDCCH def _allocate_pdcch(self, priority_list: List[Dict]) -> List[Dict]: self.pdcch_manager.reset_tti() ues_with_pdcch = [] for user in priority_list: cqi = self._get_wb_cqi(user['UE_ID']) required_cce = self.pdcch_manager.get_aggregation_level(cqi) if self.pdcch_manager.allocate_cce(user['UE_ID'], required_cce): user['allocated_cce'] = required_cce ues_with_pdcch.append(user) return ues_with_pdcch
Этап 6
PDSCH Grid Allocation & Физическое распределение ресурсов
_allocate_pdsch(tti, ues_with_pdcch, eligible_ues) O(K · N_PRB) или O(N_RBG · K) Сетка: RES_GRID_LTE

Физическое назначение ресурсных блоков в 2D частотно-временной сетке RES_GRID_LTE. Гарантирует строгое отсутствие межпользовательских коллизий. В TD-планировщиках блоки выделяются последовательно согласно общему приоритету; в частотно-селективных FD-планировщиках каждый RBG достается абоненту с наилучшим субдиапазонным качеством радиоканала (Multi-User Diversity Gain).

⚙️ Пошаговый алгоритм выполнения
  1. Сброс сетки ресурсов: Очистка матрицы распределения на текущий субкадр RES_GRID.RESET_SLOT().
  2. Реализация политики распределения:
    • TD-планировщики (RR, BestCQI, PF): Кандидаты получают последовательные группы PRB вызовами ALLOCATE_RB_PAIR() до исчерпания буфера или всех 50 PRB соты.
    • FD-планировщики (FD_PF, FD_BCQI, FD_RR): Итерация по каждому физическому блоку RBG_idx ∈ [0..16]. Назначение RBG абоненту, максимизирующему матрицу субдиапазонного приоритета argmaxi Pi,rbg. Вызов ALLOCATE_RBG().
  3. Формирование карты распределения: Заполнение результирующего словаря allocation: Dict[UE_ID, List[int]], связывающего ID терминала со списком назначенных PRB.
Фундаментальный инвариант бесколлизионного распределения:
Ri ∩ Rj = ∅ ∀ i ≠ j (Ортогональность радиоресурсов)
∑i |Ri| ≤ NPRB (Общая емкость сетки: 50 PRB для 10 МГц)
📋 Контракт данных и параметры
Входные данныеues_with_pdcch: List[Dict], объект self.lte_grid
Выходные данныеСловарь allocation: Dict[int, List[int]] (ID → индексы PRB)
Емкость соты10 МГц LTE = 50 PRB = 17 RBG (размер RBG = 3 PRB)
💡 Числовой пример из симуляции (FD)
В частотно-селективном FD_PF планировщике RBG #0 достается UE #01 (субдиапазонный CQI = 14), RBG #1 достается UE #89 (CQI = 13), RBG #2 достается UE #04 (CQI = 12). Все 50 PRB распределены между 8 абонентами с суммарной утилизацией сетки 100%.
⚠️ Преимущество частотной селективности (FD)
Благодаря многопользовательскому разнесению (Multi-User Diversity) разные абоненты находятся на пиках замирания на разных частотах. FD-планировщик дает прирост суммарного throughput соты до +25–30% по сравнению с обычным широкополосным TD-планировщиком.
# PyScheduler/SCHEDULER.py (FDxProportionalFairScheduler) def _allocate_pdsch(self, tti: int, ues_with_pdcch: List[Dict], eligible_ues: List[Dict]) -> Dict: allocation = {u['UE_ID']: [] for u in ues_with_pdcch} for rbg_idx in range(self.lte_grid.rbg_count): best_ue = max(ues_with_pdcch, key=lambda u: self._get_sb_cqi(u['UE_ID'], rbg_idx) / max(u['ue'].average_dl_throughput, 1.0)) assigned_rbs = self.lte_grid.ALLOCATE_RBG(best_ue['UE_ID'], rbg_idx) allocation[best_ue['UE_ID']].extend(assigned_rbs) return allocation
Этап 7
Grant Generation & Обработка буферов BS (TBS Extract)
_process_buffers(tti, users, allocation) O(K) Обновление: EWMA Throughput

Трансляция физических ресурсов PRB в протокольные блоки данных транспортного уровня MAC. Модуль AMC рассчитывает размер транспортного блока (TBS в байтах). Формируются объекты SchedulingGrant, из очередей BufferManager базовой станции извлекаются пакеты, при необходимости выполняется фрагментация split_packet(), и обновляется скользящая средняя скорость передачи абонентов по формуле EWMA.

⚙️ Пошаговый алгоритм выполнения
  1. Определение объема гранта: Для каждого терминала с len(allocation[ue_id]) > 0 рассчитывается емкость в байтах: tbs_bytes = (len(rbs) * bits_per_rb) // 8.
  2. Формирование SchedulingGrant: Создается объект гранта grant = SchedulingGrant(ue_id, num_bytes=tbs_bytes, ndi=True).
  3. Извлечение пакетов из буфера: Вызов buffer_manager.get_packets(ue_id, tbs_bytes).
  4. Фрагментация пакетов (RLC Segmentation): Если размер гранта не совпадает с границей целого IP-пакета, вызывается метод buffer_manager.split_packet(), фрагментирующий пакет без потерь данных.
  5. Списание данных и обновление статистики: Вызов ue.UPD_DL_THROUGHPUT_BPS(transmitted_bytes) пересчитывает среднюю скорость по экспоненциальному фильтру EWMA.
Расчет размера транспортного блока TBS и фильтрация скорости EWMA:
TBSбайты = ⌊ (Nвыделенных_PRB · BitsPerRB(CQI)) / 8 ⌋
T̅i(t+1) = (1 - 1/tc) · T̅i(t) + (1/tc) · Rinst,i(t), где tc ≈ 50..100 тактов
📋 Контракт данных и параметры
Входные данныеtti: int, users: List[Dict], allocation: Dict
Вызов BufferManagerbuffer_manager.get_packets(ue_id, num_bytes)
Вызов UE Moduleue.UPD_DL_THROUGHPUT_BPS(bytes_sent, tti)
💡 Числовой пример из симуляции
Терминалу UE #01 выделено 8 PRB при CQI = 14 (64-QAM, ~688 бит/PRB). Размер TBS = ⌊8 × 688 / 8⌋ = 688 байт. Из буфера базовой станции извлекается пакет размером 500 байт и фрагмент 188 байт от следующего пакета. Буфер уменьшается, а переданные 688 байт регистрируются в статистике такта.
⚠️ Протокольная точность фрагментации
Реализация split_packet() в PyScheduler в точности моделирует поведение подуровня RLC (Radio Link Control) стандартов 3GPP LTE/5G NR: пакет делится на сегменты с сохранением порядкового номера SN для последующей бесшовной сборки на стороне UE.
# PyScheduler/SCHEDULER.py: Извлечение данных из буферов и обновление throughput def _process_buffers(self, tti: int, users: List[Dict], allocation: Dict) -> None: buf_mgr = self.lte_grid.bs.buffer_manager for user in users: ue_id = user['UE_ID'] rbs = allocation.get(ue_id, []) if rbs: cqi = self._get_wb_cqi(ue_id) max_bytes = (len(rbs) * self.amc.GET_BITS_PER_RB(cqi)) // 8 packets = buf_mgr.get_packets(ue_id, max_bytes) tx_bytes = sum(p['size'] for p in packets) user['ue'].UPD_DL_THROUGHPUT_BPS(tx_bytes)
Этап 8 (Сводка)
Result Formation & Синтез телеметрии такта
_build_result() / _update_stats() O(1) Возврат: SimulationManager

Финальный синтез результатов планирования за текущий 1-миллисекундный субкадр. Формирует единый структурированный кадр телеметрии: суммарная утилизация PRB сетки (PRB Utilization %), среднее число ресурсных блоков на активного абонента, профиль временных задержек этапов планировщика (в микросекундах) и передает агрегированный словарь модулю верхнего уровня SIMULATION_MANAGER.py.

⚙️ Пошаговый алгоритм выполнения
  1. Подсчет выделенных PRB: Суммирование allocated_rbs = sum(len(rbs) for rbs in allocation.values()).
  2. Подсчет активных абонентов: Подсчет active_ues = sum(1 for rbs in allocation.values() if len(rbs) > 0).
  3. Расчет эффективности: prb_utilization_pct = (allocated_rbs / total_rbs) * 100%.
  4. Сохранение профиля таймингов: Запись sch_time_us, priority_calc_time_us, priority_sort_time_us.
  5. Возврат объекта кадра: Вызов _build_result() возвращает сформированный кадр субкадра для логирования и отображения на графиках.

💡 8. Инженерные выводы и ключевые инварианты такта

Фундаментальные принципы корректности моделирования беспроводной сети в масштабе реального времени

⏱️ 1. Строгая синхронизация 1000 Гц
Все 12 модулей симулятора замкнуты в общий синхронный контур частотой 1000 Гц (шаг 1 мс). Любое действие — генерация пакетов, кинематика координат, замирания радиоканала, распределение ресурсов — привязано к системной метке GLOBALS.CURRENT_TIME = tti.
🛡️ 2. Двухконтурность PDCCH + PDSCH
Абонент не может получить ресурсы PDSCH в обход канала управления PDCCH. Терминал обязан получить грант CCE (агрегация 1, 2, 4 или 8). При дефиците емкости CCE кандидат блокируется, даже если в спектре PDSCH остались свободные ресурсные блоки.
📦 3. Материальный баланс данных
Замкнутый контур сохранения данных: байты из генератора трафика → RLC-буфер базовой станции → выдача гранта SchedulingGrant → списание ровно $TBS$ байт через extract_data() → фрагментация split_packet(). Ни один бит не теряется и не генерируется фиктивно.
⚡ 4. Потенциал распараллеливания
Самые ресурсоемкие этапы миллисекундного такта — пространственные замирания 3GPP TR 38.901 (TDL-A..E и SINR) и кинематика перемещений — полностью независимы для каждого UE и подготовлены для выполнения в многопоточном пуле воркеров.
